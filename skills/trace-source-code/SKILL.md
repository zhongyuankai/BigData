# Trace Source Code

## 目标与适用场景

跟踪函数、类或子系统的真实源码实现，并将结果整理为容易理解的中文 Markdown 文档。

- 根据目标规模调整深度；简单函数省略不适用内容。
- 大型子系统先给出拆分建议和文档边界，确认后再生成多篇文档。
- 只分析和解释当前源码，不修改被跟踪的实现。

## 源码跟踪流程

1. 判断目标是函数、类还是子系统；范围不明确时询问一个关键问题。
2. 沿真实源码跟踪调用入口、核心实现、关键分支、状态或数据变化、下游副作用、异常边界和相关测试。
3. 为关键结论寻找直接源码证据；证据不足时说明缺失环节，不根据名称或惯例猜测。
4. 构造一个具体输入、对象或状态作为贯穿案例，使用它解释关键分支和状态变化。
5. 按真实执行顺序组织内容并写入 Markdown 文档。
6. 在文档所属仓库的 `README.md` 中同步维护该文档的索引。
7. 完成内容与链接检查后，将本次文档和索引变更提交 commit，并推送到对应远端分支。

## 文档可读性要求

- 固定使用中文说明；类名、方法名、字段名、配置项、日志和代码保持原文。
- 先说明目标代码解决的问题和整体调用链，再进入方法细节。
- 正文直接进入分析对象的职责与机制；不写仓库提交号、本地源码绝对路径、统一源码或测试路径前缀说明，以及“不混入其他版本”等分析过程声明。版本与路径核对在分析过程中完成，不写入源码分析文件；用户明确要求记录这些信息时遵从。
- 按执行顺序说明每个关键阶段：从哪里调用、做了什么、改变了什么、为什么这样实现、下一步到哪里。
- 关键结论使用 `源码文件:行号` 标注位置，不生成 Markdown 源码链接。
- 只摘录理解流程所需的短小代码片段，并结合上下文解释，避免堆砌源码。
- 使用具体数值、状态表或输入输出辅助理解。
- 只有复杂状态转换、异步调用或多组件协作时才使用 Mermaid 图。
- 将疑似缺陷、注释与实现不一致或并发风险放入独立的“源码审阅发现”章节，区分源码事实、推断和待验证项。
- 最后用简短心智模型总结完整流程，并给出推荐源码阅读顺序。
- 省略与当前目标无关的章节，不为套用结构而扩写。

## 输出与索引

- 默认根目录：`/Users/didi/zyk/doc/github/BigData`。先读 README 和现有目录，按主题归类，如 `ElasticSearch/`、`Kafka/`、`Java/Thread/`、`Java/Jvm/`；无合适目录再创建，不静默回退到源码仓库。
- 同目标、同范围的已有文档优先原地更新并保留旧文件名。新文件使用小写连字符主题名，如 `replication-tracker.md`，不加 `source-trace` 或编号；用户指定路径或文件名时遵从。
- 同步项目根 `README.md`：在对应主题章节维护唯一条目，使用有效相对链接，重命名时同步修正；缺少章节或 README 时按现有风格补建，不整理无关条目。空格路径用尖括号或 URL 编码。
- 指定其他输出位置时，项目根取目标 Git 仓库根；非 Git 目录取用户指定的文档目录。用户限定只输出单文件时，只写该文件，跳过索引、提交和推送。

## 验证与发布

1. 核对源码位置、代码片段、事实边界、案例、代码围栏、Markdown 空白及本次 README 链接；检查并移除文档中的仓库提交号、本地源码绝对路径、路径前缀说明和分析过程声明，保留必要的 `源码文件:行号` 证据。文档任务不默认运行大型构建或测试。
2. 在文档仓库检查指南、分支、远端、上游和工作区状态，审阅本次 diff。只提交本次文件和差异，保留无关暂存及未暂存改动；同文件已有改动也需隔离，用户明确纳入整文件时除外。可用 `git commit --only -- <本次文件>` 限定路径。
3. 默认创建概括主题的 commit，推送到已配置的对应远端分支，并核实远端包含该提交。无变更时跳过提交和推送；仅重试已确认属于本任务的失败推送。遵从用户不提交、不推送等明确要求。
4. 待推送范围含无关提交、无法隔离改动、目录不可访问、缺少可用 Git 仓库/分支/远端，以及鉴权或推送失败时，保留成果并报告阻塞；不自动初始化仓库、搬运提交、重写历史或强推。
5. 最终报告文档路径、README 更新、commit 和推送结果；未完成步骤如实说明。
