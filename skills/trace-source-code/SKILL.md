# Trace Source Code

## 目标与适用场景

跟踪函数、类或子系统的真实源码实现，并将结果整理为容易理解的中文 Markdown 文档。

- 根据目标规模调整深度；简单函数省略不适用内容。
- 大型子系统先给出拆分建议和文档边界，确认后再生成多篇文档。
- 只分析和解释当前源码，不修改被跟踪的实现。

## 源码跟踪流程

1. 判断目标是函数、类还是子系统；范围不明确时询问一个关键问题。
2. 沿真实源码跟踪调用入口、核心实现、关键分支、状态或数据变化、下游副作用、异常边界和相关测试。
3. 为关键结论寻找直接源码证据；证据不足时说明缺失环节，不根据名称或惯例猜测。
4. 构造一个具体输入、对象或状态作为贯穿案例，使用它解释关键分支和状态变化。
5. 按真实执行顺序组织内容并写入 Markdown 文档。
6. 在文档所属仓库的 `README.md` 中同步维护该文档的索引。
7. 完成内容与链接检查后，将本次文档和索引变更提交 commit，并推送到对应远端分支。

## 文档可读性要求

- 固定使用中文说明；类名、方法名、字段名、配置项、日志和代码保持原文。
- 先说明目标代码解决的问题和整体调用链，再进入方法细节。
- 按执行顺序说明每个关键阶段：从哪里调用、做了什么、改变了什么、为什么这样实现、下一步到哪里。
- 关键结论使用 `源码文件:行号` 标注位置，不生成 Markdown 源码链接。
- 只摘录理解流程所需的短小代码片段，并结合上下文解释，避免堆砌源码。
- 使用具体数值、状态表或输入输出辅助理解。
- 只有复杂状态转换、异步调用或多组件协作时才使用 Mermaid 图。
- 将疑似缺陷、注释与实现不一致或并发风险放入独立的“源码审阅发现”章节，区分源码事实、推断和待验证项。
- 最后用简短心智模型总结完整流程，并给出推荐源码阅读顺序。
- 省略与当前目标无关的章节，不为套用结构而扩写。

## 默认输出规则

- 用户指定目录或文件名时使用用户提供的值。
- 未指定目录时，以 `/Users/didi/zyk/doc/github/BigData` 为默认文档项目根目录，先查看该项目的 `README.md` 和已有目录，再按内容选择位置；不要默认写入被分析的源码仓库。
- 优先复用已有主题目录和子目录。例如 Elasticsearch 使用 `ElasticSearch/`，Kafka 使用 `Kafka/`，Java 并发使用 `Java/Thread/`，JVM 使用 `Java/Jvm/`。跨主题内容按主要分析对象归类；没有合适目录时再创建语义明确的主题目录。
- 文档目标项目不存在或不可访问时，说明实际阻塞，不静默改回源码仓库或其他位置。
- 未指定文件名时，将主题名规范化为小写连字符文件名并添加 `.md`，不附加 `source-trace`。例如 `ReplicationTracker` 输出为 `replication-tracker.md`。
- 写入前检查是否已有同一分析目标、范围相同的文档；已有时优先更新原文件并保留现有文件名，即使旧名不符合新命名规则。不同范围的文档可分别保留。同名文件存在时更新原文件，不生成编号副本；输出目录不存在时创建目录。
- 不在文档中记录仓库名、分支、提交 SHA 或生成日期。

## README 索引同步

- 默认维护 `/Users/didi/zyk/doc/github/BigData/README.md`，在与主题对应的章节添加或更新文档条目；没有对应章节时沿用现有风格新增章节。
- 链接使用相对 README 所在目录的路径；文件名有空格时使用 Markdown 尖括号目标或正确的 URL 编码。标题应让读者理解主题。
- 同一篇文档只保留一个索引条目；更新或重命名时同步修正原条目，不重复追加，不顺手整理其他条目。
- 用户明确限定只输出单个文件时，跳过 README 更新、commit 和 push。
- 用户指定 BigData 之外的输出位置且未限定单文件时，以目标 Git 仓库根为项目根维护 README；非 Git 目录以明确指定的文档目录为根，没有 README 时创建简短索引。不向 BigData 添加指向仓库外本地文件的链接。

## Git 提交与推送

- 默认完成“文档落盘 → README 同步 → 验证 → commit → push”。用户明确要求只分析、不提交、不推送或使用其他目标时，遵从该次要求；本 skill 不授权修改被分析的源码实现。
- 在文档所属 Git 仓库执行操作，先检查仓库指南、当前分支、远端、上游关系及 `git status --short`。记录已有的暂存和未暂存改动，保护用户工作。
- 审阅本次文档和 README 的完整 diff，检查 Markdown 空白、代码围栏和本次新增或更新的索引链接；文档改动不默认运行源码项目的大型构建或测试。
- 只提交本次生成或更新的文档与 README，使用明确的文件路径；避免 `git add .`、`git add -A` 或会混入无关暂存文件的提交方式。必要时使用 `git commit --only -- <本次文件>`，保留其他暂存内容。
- 同一目标文件已有用户改动时，区分本次差异与原有内容；用户已明确将整个文件纳入任务时可整文件提交，否则隔离本次内容后提交。无法可靠隔离时，保留成果并说明提交阻塞，不能认为限定路径就隔离了文件内部的无关改动。
- 提交消息概括分析主题，例如 `docs: explain retention lease recovery`。文档和 README 均无本次变更时，不创建空提交，默认跳过推送；仅在已确认存在先前推送失败、属于本次任务的提交时重试推送。
- 按目标仓库指南选择分支；已有合适工作分支时继续使用。向已配置的对应远端分支推送，核对待推送提交范围，避免意外发布无关本地提交。不猜测远端地址或分支，不强制推送。
- 待推送范围包含无关本地提交时，保留本次本地提交并停止推送，说明阻塞，待用户指定处理方式；不自动搬运提交或发布无关历史。
- 遇到非 Git 目录、detached HEAD、缺少远端或分支目标不明确、鉴权失败、远端拒绝推送时，保留已完成的文件和本地提交，说明阻塞及所需信息。不自动初始化仓库、重写历史或覆盖远端。
- 推送成功后，核对远端目标分支包含本次提交。最终报告文档路径、README 更新、commit 标识和推送结果；推送失败时不能报告全部完成。

## 完成前检查

- 确认引用的源码文件和行号存在。
- 确认代码片段与当前源码一致。
- 确认正文先讲整体流程，再讲实现细节，并包含贯穿案例。
- 确认事实、推断和待验证项没有混写。
- 确认没有未完成内容，所有代码围栏均已闭合。
- 确认文档按主题落在正确目录，README 中对应链接有效且没有重复条目。
- 确认本次 commit 仅包含目标文件、无关改动保持原状，并已核实远端推送结果；如用户要求跳过某步，明确说明。
