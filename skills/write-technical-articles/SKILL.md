# 中文技术文章写作

面向具备技术基础、但未必熟悉当前系统的同行。使用自然、准确的书面中文，让读者能顺着文章理解：系统怎样运行，问题在什么条件下出现，为什么选择这个方案，以及改造带来了什么变化。

## 从读者关心的问题切入

开头尽早提出本文要回答的问题。业务背景写到足以说明“为什么值得解决”为止。读者熟悉的产品可以直接进入主题，专有组件在第一次参与流程时再介绍。

根据技术问题选择叙述主线，章节按实际材料取舍。

| 文章类型 | 适合的主线 |
|---|---|
| 架构设计与升级 | 现有架构怎样工作 → 遇到了什么限制 → 为什么这样设计 → 改造后如何运行 |
| 技术原理与源码解析 | 提出一个行为问题 → 找到执行入口 → 沿关键路径追踪 → 解释结果怎样产生 |
| 性能优化 | 描述负载与现象 → 定位耗时或资源开销 → 解释优化机制 → 给出实测结果 |
| 故障复盘 | 描述影响 → 沿证据定位原因 → 解释止损和恢复过程 → 交代改进措施 |

每提出一个主要问题，后文都应有对应的解释或解决办法。相邻章节反复讲同一现象时，保留解释最充分的一处，其余位置用一句话衔接。

## 沿实际运行路径讲清机制

选择一条读者能跟住的线索，例如一次请求、一条数据、一段调用链或一个对象的状态变化。沿着它说明谁发起动作、谁负责处理、满足什么条件后进入下一步。类名、方法名、配置项和 API 只在有助于定位或理解机制时出现，并用内联代码标记。

关键设计多解释一层“为什么”。尤其关注看似可以省略的等待、必须遵守的操作顺序、可以复用的已有能力，以及方案成立所依赖的前提。写性能优化时，点明原来具体做了哪些工作、代价在哪里、改造后省去了哪部分开销。

描述切换或迁移时，要交代中间状态。例如，路由已经更新、客户端已经拿到新地址、目标节点已经能够处理请求，这几个时点可能不同。只要差异会影响业务，就写清楚在这个阶段哪些操作能够成功、哪些仍需等待。

长流程按目的归纳成几个阶段。每个阶段围绕一个主要动作，说明执行后的状态。正常与故障流程、旧实现与新实现并列出现时，在开头点明当前讨论的场景，前后使用一致的角色名称。

## 在每个关键理解点配图

构思时逐节判断：读者在这里需要看清哪段关系、顺序、状态或差异，才能理解后面的结论？凡是影响核心机制、设计取舍或改造收益的关键理解点，都要在对应位置用图说明。图的数量和位置由正文中的关键理解决定。

| 读者需要理解什么 | 适合的图 | 图中要表达清楚的内容 |
|---|---|---|
| 系统由哪些组件组成，请求和数据怎样流动 | 架构图、数据流图 | 组件职责、系统边界、流向。箭头标明具体动作，例如“转发写请求”“复制数据”。 |
| 多个组件如何协作，为什么要按这个顺序执行 | 时序图 | 发起方、接收方、先后顺序，以及等待、确认和生效的时点。 |
| 对象怎样改变状态，中间阶段能做什么 | 状态图，或带状态标注的时序图 | 触发条件、状态变化，以及与读者有关的可用能力。 |
| 改造究竟改变了哪里，优化为何有效 | 前后对比图 | 对齐相同的起点、终点和组件名称，突出移除的步骤、改变的依赖或缩短的路径。 |
| 指标如何随时间、负载或规模变化 | 折线图、柱状图等数据图 | 使用实测数据，标明单位、测试条件和比较对象。只有一组前后值时，可以直接标在对比图旁。 |

图放在对应论述附近。图前用一句话指出要观察的问题，图后解释最重要的因果关系。图中已经清楚展示的步骤，正文可以按阶段归纳，把篇幅留给“为什么这样做”。

几个紧密相关的要点可以共用一张图。如果一张总览图只展示了组件部署，后文又要解释某条依赖是如何移除的，就在该节补充前后对比图。正常与异常流程的顺序和前提差异较大时，分别画图。

交付可直接使用的图。沿用目标文档支持的格式，Markdown 中可以使用 Mermaid。续写已有文章时，优先检查现有图能否覆盖新增内容，需要时补图或调整标注。

## 让结论与证据相称

根据材料区分设计意图、代码行为、上线状态和实测结果。设计文档说明计划怎么做，代码说明实现支持什么，部署记录和测量结果分别支撑上线范围与实际收益。缺少某一层证据时，把结论限定在材料能够支持的范围内。

写性能数据时，将测试场景和结果放在一起。给出影响理解的负载、数据规模、操作类型、指标及前后值。不同场景或不同阶段的耗时要写明计时范围，尤其注意区分局部操作耗时和端到端恢复时间。

例如：“在一个包含 84 个分区、平均每个分区约 5 TB 的线上索引上，正常主从切换耗时从 177 秒降至 19 秒。”这句话同时交代了规模、操作类型和结果，读者能判断数据适用于什么场景。

使用“保证”“实时”“无损”“完全恢复”等词时，说明相应机制和成立条件。如果设计只能降低风险，就解释它降低了什么风险，以及在什么情况下风险仍然存在。示例中的组件和数字仅用于说明写法，新文章以本次材料为准。

## 保持自然、简洁的技术表达

使用同行交流的口吻。一段集中回答一个问题，用“更新路由”“解除写入限制”“复用已有引擎”这类具体动作说明变化。写到“提升稳定性”或“降低开销”时，继续指出哪条依赖被移除、哪项操作被省去，或业务能观察到什么改善。

标题提示本节要回答的问题。段落之间通过因果关系、条件变化或上文留下的问题自然衔接。架构本身已经足够清楚时，直接讲机制；业务故事、类比和具体案例按读者需要使用。

总结回到开头的问题，保留最重要的能力变化和有代表性的结果。后续计划与已经验证的效果分开表述。

## 续写、润色与审阅

- **续写**：先读相邻章节，沿用作者的术语、视角和详略。从前文留下的问题接着写，只补用户指定的部分。
- **润色**：保留原意、事实和作者口吻，优先处理歧义、重复、过长的句子和跳跃的因果关系。
- **审阅**：先核对技术行为、流程顺序和数据口径，再检查每个关键理解点是否有相应的图、图文是否一致，最后处理结构和措辞。指出具体位置、可能造成的误解，并在有帮助时给出可直接替换的文字。

交稿前顺着正文和图完整走一遍。如果读者仍需自行拼出一条关键路径、推演一个重要的中间状态，或来回翻阅才能找到改造前后的差异，就在对应位置补图或补一句解释。
